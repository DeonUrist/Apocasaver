# Apocasaver 2.0.2 save policy verification

11 October 2026. Corrects the 2.0.0/2.0.1 strict completion checks: a save attempt must not be rejected for a compatibility
or semantic check. Actual disk persistence failures still restore the previous destination and warn the player.

Validation on the final build:

- Release build: zero warnings/errors.
- 100 managed filesystem, policy, inventory compatibility and autosave checks.
- 57 native Unity companion checks: `verification/results/mods-20261011-030028/report.txt`.
- 42 native Unity no-companion checks: `verification/results/vanilla-20261011-030100/report.txt`.
- Installed native hook/cache and companion signatures verified; `git diff --check` clean.

Native regressions cover missing object/write confirmations, an unavailable save-button FSM, a missing optional binding,
confirmation timeout, registered-object changes, a candidate that becomes protected, native fallback without slot deletion,
superseding an older recovery journal, terrain history captured during saving and delayed file-only mod state carried into
a new slot. Cleanup cancellation verifies that the retained candidate is present in the actual serialized registration array.
Both an injected IO error and a real exclusive file lock on the ES3 staging destination restore the previous slot byte-for-byte.

Source records are preserved until fresh native writes replace them; known absent object records and obsolete moving-hinge
position records are removed during normal rebuilding. Unknown/opaque records and unloaded location history are retained.
When compatibility prevents rebuilding, the native cache still inherits source-playthrough data where that cache API is
available. Each optional companion retains its own prior state when unavailable, without discarding another companion's
successful fresh snapshot. Cleanup is skipped when preservation cannot be confirmed.

The fixtures use real Unity, Harmony, ES3 and installed companion assemblies, with isolated save paths and constructed
native FSMs. They do not replay a full interactive or long-session game. The player's attachment remains truncated before
the actual reported failure; this release corrects the save policy and tested rejection paths, rather than claiming an exact
reproduction of that player's missing exception. A completion warning means native freshness was not fully confirmed;
the mod writes available data and retains previous useful records instead of treating the warning as a save failure.
